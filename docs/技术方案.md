## 0. 结论摘要

1. **技术内核不是"生成学习计划"**，而是三件事：自定义计划格式（可被人和机器共同维护）、确定性的重排引擎、带出处的主动信息获取。
2. **开发方式以 AI 生成为主**，因此工期估算必须按「人类介入的迭代循环」而非「人写代码的小时数」来算。按此模型，总人类投入约 **15–28 人时**，相对 106 人时的预算有 3–5 倍冗余。
3. **冗余应全部投给 P4（试用与调整）**。这个项目的成败在"好不好用"，不在"功能多不多"。
4. 产品形态：**Expo (React Native) 移动端 App**，走赛道 2 亦可兼报。开发时**浏览器优先**（react-native-web），真机只做验收。

## 1. 成本模型：AI 辅助下真正的瓶颈

AI 把打字成本压到接近零。成本只留在人类必须介入的地方。因此单位不是人时，而是**迭代循环数 × 每轮人类决策成本**。

| 循环 | 内容 | 人时成本 |
|---|---|---|
| T1 生成 | AI 写代码、写测试、改 bug | ≈ 0 |
| T2 验证 | 人看结果 → 决定改什么 | **5–20 min/轮** |
| T3 反馈 | 热重载 / 真机重载 / 原生构建 | 1 s / 5–30 s / 2–10 min |
| T4 排错 | 报错 → 交给 AI → 修 | 5–15 min/轮（AI 能自测的 bug 趋近 0） |
| T5 试用 | 真人用产品 → 提意见 → 改 | **30–60 min/人/轮** |

### 三条关键推论

**推论 1：AI 压不动 T2 和 T5，而它们占本项目成本的 70% 以上。**
工程目标因此不是"少写代码"，而是**压缩观察循环**。

**推论 2：只有"纯函数 + 单测"这一层，AI 才能真正闭环。**
把命令层、规则层、校验层全部做成无副作用的纯函数，AI 可以自己跑测试自证正确，这部分 T2/T4 完全移出人类预算。

**推论 3：浏览器优先开发能砍掉 T3 的绝大部分。**
Expo + react-native-web 让同一套组件在浏览器里跑 HMR（秒级），视觉迭代轮数不变但每轮便宜约 30 倍。真机只在里程碑节点验收。

### 三条对应的架构决策

| 决策 | 目的 |
|---|---|
| **A. 浏览器优先**（react-native-web + HMR） | 压缩 T3 |
| **B. 逻辑下沉到纯函数层**（命令 / 规则 / 校验 + 单测） | 把 T2/T4 移出人类预算 |
| **C. 开发期场景切换器**（一键跳到任意状态） | 压缩 T2，并让多人并行试用 |

## 3. 系统架构

```
apps/mobile  (Expo + expo-router + react-native-web)
   │  HTTP/JSON（唯一通道，且只是「有服务端时更好」）
   ▼
apps/server  (Fastify + zod)
   ├─ routes/     薄路由层，只做 IO 与参数校验
   └─ tools/      唯一真的发 HTTP 的地方：codeforces.ts（实时赛事）
   ▲
   │  引用
packages/shared   ← 唯一真相源，可在 Hermes 上跑（断网时 App 全靠它）
   ├─ plan/schema.ts      格式定义 + 语义校验
   ├─ plan/commands.ts    命令层（纯函数）
   ├─ plan/engine.ts      自适应引擎（纯函数）
   ├─ llm/                契约 + 提示词 + 本地兜底（不碰网络）
   └─ tools/              资料库 + 确定性检索（不碰网络）
```

**为什么要有后端**：LLM API Key 不能进 App——移动端反编译拿 Key 是必然的。
另外工具调用里**唯一真正需要服务端**的是实时赛事抓取（要发 HTTP）。
资料检索是纯本地的，断网时 App 用同一份代码照样给得出资料。

> 图上刻意去掉了 NativeWind / Reanimated / SQLite：实现时都没用
> （理由见 §9.3、§9.4）。**参赛文档里写着一个库里没有的东西，比不写更糟。**

**但后端要薄**：所有逻辑在 `packages/shared`，服务端只做转发和持久化。这样逻辑层可以被 AI 单测覆盖，且 Web 端/命令行也能复用同一套逻辑。

## 4. 数据格式规范：`studyplan/v1`

### 4.1 「自定义格式」的边界（重要的设计决策）

**自定义的是 schema 和语义，不是语法。** 本格式使用 YAML 子集作为序列化语法，文件后缀 `.studyplan`。

理由：

| 方案 | 成本 | 收益 |
|---|---|---|
| 从零发明语法（自写 parser） | 2–4 天，且边界情况无穷；解析器 bug 会污染整个流程 | 答辩故事好听一点 |
| **YAML 子集 + 自定义 schema（本方案）** | 半天（用 `js-yaml`） | 人可读、可手改、编辑器有高亮、解析器零风险 |

真正体现"自定义"的地方在于，YAML 表达不了的东西全部由 schema 承担：

- **语义化状态机**：`todo / doing / done / skipped / blocked`。`skipped`（意愿问题）和 `blocked`（条件问题）严格区分，因为二者触发的重排策略完全不同。
- **引用完整性**：所有跨实体引用用 id。
- **不变量**：`dependsOn` 必须无环、前置任务不得排在后置之后、排期不得落在 blackout 内、周排期不得超过周预算。
- **证据链**：能力点掌握度的每次更新都记录 `evidence`，保证"为什么系统认为你掌握了"可回答。

> 如果团队坚持要"看得见的自定义语法"，可以在 YAML 之上加一段紧凑的任务块序列（类似 ICS 的行格式）作为可选的人写入口。但这是 P5 之后的事，不要提前做。

### 4.2 文件结构

```
studyplan/v1
├─ schema        "studyplan/v1"          版本迁移锚点
├─ id / version                           每次 applyCommand 成功后 version +1
├─ meta          title, created, updated, origin
├─ goal          statement（保留学生原话）, successCriteria[], deadline, priority
├─ constraints   weeklyMinutes, availableSlots[], maxSessionMinutes, blackouts[]
├─ profile       学生档案：目标 / 截止日 / 水平 / 每周可投入时间 / 学习日 / 薄弱点 / 要避开的整段
│                     它是**关于这个学生的**，不是关于这台设备的——所以住文件里，不住设置里
├─ competences[] 能力点：target / current / evidence[]   ← 引擎的实际操作对象
├─ milestones[]  里程碑：due / competenceIds[] / criteria[]
├─ tasks[]       任务：dependsOn[] 构成 DAG, estimateMin, type, status,
│                      scheduledFor（null = 待排池）, pinned（学生锁定）, notBefore（最早可排日）,
│                      actualMin, difficulty, tags[]
├─ resources[]   url / kind / verifiedAt / source        ← verifiedAt 是"非幻觉"的证据
├─ tags[]        标记目录（学生自定义的那部分，内置的在代码里）
├─ reviews[]     复盘记录：kind（review / settle）/ 完成率 / 自评负载 / 产生的调整 / dialogue
└─ history[]     只追加的命令摘要（回滚靠版本快照，不靠重放）
```

**实体关系**

```
Goal ──▶ Milestone ──▶ Competence ──▶ Task ──▶ Resource
                          ▲            │
                          └── evidence ┘
```

- `Task` 是**手段**，`Competence` 是**目标**。这是本设计区别于"待办清单"的核心：待办清单只优化"做完"，本系统优化"能力增长"。
- 一个任务可以同时服务于多个能力点（当前用 `milestoneId` 单挂，V2 可扩为多挂）。

完整定义见 `packages/shared/src/plan/schema.ts`，示例见 `examples/demo.studyplan`。

### 4.3 版本与迁移

- 顶层 `schema` 字段是迁移锚点。`migrate(raw)` 按 schema 分发转换函数。
- 每次成功变更，把**整份快照**写入 `versions/v{n}.studyplan`。文件很小（几十 KB），不值得优化。
- **回滚不靠重放命令**。重放要求命令永久向后兼容，代价高且容易错；快照恢复简单可靠。
- 回滚本身也产生新版本（`version + 1`），历史不可改写。

## 5. 命令层规范

**铁律：任何状态变更都必须走 `applyCommand`，前端不允许直接改 plan 对象。**

```ts
applyCommand(plan: PlanFile, cmd: Command): ApplyResult
//  纯函数：不读时钟、不读网络、不读随机数。所有时间从 cmd.at 传入。
//  流程：structuredClone → execute（就地改） → validatePlan → version+1 → 追加 history
```

命令集合（完整定义见 `packages/shared/src/plan/commands.ts`）：

| 命令 | 说明 |
|---|---|
| `task.setStatus` | 标记状态；**标记 done 时校验前置任务是否完成** |
| `task.setEstimate` | 修改预估时长 |
| `task.reschedule` | 改期或移回待排池（`scheduledFor: null`） |
| `task.edit` / `task.add` / `task.remove` | 增删改；删除时自动清理他人的悬空依赖 |
| `goal.update` / `constraints.update` | 目标与约束变更 |
| `competence.update` | 掌握度更新 + 记录证据 |
| `resource.add` | 新增资源（工具调用结果） |
| `plan.applyAdjustments` | 复盘协商：一次性写回学生接受的调整批次 |
| `plan.restore` | 从快照回滚 |

**为什么必须这样设计**：这是本项目里唯一能"让 AI 自己验证自己"的部分。纯函数 + 单测，AI 生成后可以直接 `pnpm test` 自证，人类不需要读代码。这直接对应第 1 节的推论 2。

必写的单测（让 AI 生成，人类不读）：

1. 依赖未完成的任务不能被标记完成
2. 删除任务后，其他任务的 `dependsOn` 不留悬空引用
3. 制造环状依赖 → 校验必须报错
4. 命令时间早于 `meta.updated` → 必须拒绝
5. 回滚后 `version` 继续前进，`history` 追加而非截断
6. 每个命令执行后 `version === 旧版 + 1`
7. 排期超预算只产生 `warn`，不阻断（产品决策：允许超载但要告知）

## 6. 自适应引擎（规则层）

**核心原则：规则层负责算，LLM 负责解释和提议。** 时长超没超、依赖断没断，用代码算，可解释、可复现、不幻觉。

### 6.1 偏差检测 `detectDrift(plan, now): Drift[]`

| 偏差 | 判据 | 含义 |
|---|---|---|
| `overdue` | `scheduledFor < today && status ∈ {todo, doing}` | 落后 |
| `overrun` | `actualMin > estimateMin × 1.3` | 预估偏低，后续同类任务要上调 |
| `underrun` | `actualMin < estimateMin × 0.6` | **超前信号**，是"加内容"的依据 |
| `stalled` | `status === doing` 且 N 天无变化 | 卡住 |
| `chainBlocked` | 前置任务 overdue | 连锁延误 |
| `milestoneRisk` | 剩余任务预估总时长 > 到 due 的可用时长 | 里程碑有风险 |
| `budgetOver` | 周排期 > `weeklyMinutes` | 超载 |

### 6.2 重排 `proposeReschedule(plan, now): AppliedAdjustment[]`

```
0. 剔除 pinned 任务：它们不参与重排，但占用的时间要被预留
0b. 以 notBefore 作为每个任务的最早可排日，再与依赖日取最大
1. 按 dependsOn 做拓扑排序
2. 生成待排队列，排序键：(priority desc, milestone.due asc, 拓扑序)
3. 展开可用时间槽：availableSlots × 未来 N 周，扣除 blackouts
4. 逐个填充；超过 maxSessionMinutes 的任务切分为多个片段
5. 为已完成任务插入复习节点（简化间隔重复：+1d / +3d / +7d / +21d）
6. 未能在 horizon 内排下的任务 → scheduledFor = null（回待排池）
7. 输出为一组 AppliedAdjustment，每条带自然语言 reason
```

> **`notBefore` 是补上的一个真实漏洞。** 示例里 `t_graph01` 的备注写着
> 「等期中考试周之后再安排」，但这只是 `notes` 里的自由文本，规则层读不懂，
> 于是引擎把它排到了期中考试周**之前**。
> 学生在 LLM 的提醒里才看到这个问题——而离线降级时没有 LLM，就没人兜底了。
> **「我说了不算」比排得不优严重得多**，所以这类意图必须有结构化的表达方式，
> 并由规则层强制执行（`validatePlan` 也会在违反时给出 warn）。

**三个护栏（重要的产品决策）**：

- **单次调整幅度上限**：一次最多改动 30% 的**已有排期**任务。理由是"计划大跳变"会让学生失去掌控感，比排得不优更伤。
  注意「首次排期」（`scheduledFor` 原为 `null`）不计入这个上限——给还没排期的任务安排时间不叫折腾学生，
  而且若不区分，任务少时上限会退化成 1，连"前置任务必须排在后面"这种基本要求都满足不了。
- **难度爬升上限**：单周难度提升不超过 0.2。防止系统在"学得快"时把学生压垮。
- **手动改期自动上锁（`pinned`）**：学生通过 `task.reschedule` 手动排定的日期默认置 `pinned: true`，
  引擎不再自动挪动它，但仍会把该任务占用的时间预留出来。
  **这条是"协商"卖点的守卫**：如果系统把学生刻意避开考试周的安排又改回去，学生只会得出一个结论——
  "我说了不算"，那比排得不优的伤害大得多。

**每条调整必须给出具体理由。** 理由的措辞是学生判断"系统到底懂不懂我"的唯一依据，也是评委区分
"真自适应"与"套壳"的关键。措辞规则：

| 情境 | 措辞 |
|---|---|
| 首次排期 | `纳入排期：<日期>（此前未安排时间）` |
| 推后 | `从 <原日期> 顺延到 <新日期>（<原因>）` |
| 提前 | `从 <原日期> 提前到 <新日期>（<原因>）` |
| 排不下 | `未来 N 天内可用时段不足，排不下，先移回待排池` |

**禁止**把首次排期称作"重排"，也禁止使用"为腾出容量重排到 X"这类没有信息量的措辞。

### 6.3 掌握度更新 `updateMastery(...)`

不用完整 DKT，用可解释的指数移动平均：

```
若 task.status === done 且 task.type ∈ {practice, project, assess}：
    gain = 0.15 × (1 − difficulty) × 时长因子
    competence.current = clamp(current + gain × (1 − current), 0, 1)
    记录 evidence.push(task.id)
若 task.status === skipped：
    current 衰减 0.02（温和衰减，避免误伤）
```

`(1 − current)` 项让初期涨得快、接近目标时收敛，符合技能习得的边际递减。

### 6.4 目标协商 `proposeGoalOptions(plan): GoalOption[]`

| 触发条件 | 提议 |
|---|---|
| 连续 2 周完成率 > 0.9 且难度 < 0.4 | 加深内容 / 加速进度 / **转向相关竞赛** |
| 连续 2 周完成率 < 0.5 | 延长 deadline / 缩小范围 / 下调周目标 |
| 里程碑风险高 | 拆分里程碑 / 降低该里程碑标准 |

**每个选项必须给出「对总时长的影响」和「预计后果」**，由学生确认。绝不自动改目标。

> 产品上要避免的表述：不要写"发现你学得快，所以我们加了更多内容"。这句话在演示里会被理解成压榨。正确表述是提供选项，把决定权交回学生——这恰好也是"协商"作为卖点的意义。

## 7. LLM 契约

**只有 3 个调用点。每个都必须：structured output → zod 校验 → 失败重试 1 次 → 再失败降级到本地模板。**

### 7.0 实现方式：薄客户端，不用 AI SDK（与原方案不同）

原方案写的是「用 Vercel AI SDK」。实际实现改成**零依赖的 OpenAI 兼容薄客户端**，理由是需求变成了
「必须兼容 OpenAI 协议」：

| | AI SDK | 薄客户端（采用） |
|---|---|---|
| response_format | 走 provider 专有结构化输出 API | 默认不发；需要时发通用 `json_object` |
| 兼容端点覆盖 | 依赖各 provider 适配器质量 | 任何实现 `/chat/completions` 的端点都能用 |
| 依赖体量 | 大 | 0（只用 `fetch`） |
| 结构化可靠性 | 交给 SDK | 提示词 + 防御性 JSON 提取 + zod 校验 + **带着具体错误重试** |

最后一行是关键：**模型输出从来不会 100% 干净**，所以「提取 + 校验 + 纠错重试」这套无论如何都要写。
既然要写，SDK 的结构化输出就没带来额外价值，反而多一层需要跟着升级的依赖。

刻意避开各家不一致的地方：不发 `max_completion_tokens`（只有 OpenAI 新模型认）、
不依赖 `tool_calls` / `stream`。

### 7.0.1 代码分层（护栏驱动的切分）

| 层 | 位置 | 为什么 |
|---|---|---|
| 契约 / 提示词 / 输出校验 / 降级视图 | `packages/shared/src/llm/` | 不碰网络，且**移动端需要 `engineView`**——断网时在本机算出复盘并降级展示 |
| HTTP 客户端（provider 契约、`completeJson`、OpenAI 兼容适配器） | `packages/llm-client/` | 需要 `fetch`/`AbortController`/`setTimeout`，不适合放进维持「Hermes 可跑」护栏的 shared |

> 这个切分来自一次 typecheck 失败：把 HTTP 客户端放 shared 时，那些全局一个都找不到。
> 那正是护栏在起作用——它不是障碍，是在提示边界画错了。

### 7.0.2 LLM 是表现层，不是决策层

**引擎算，LLM 说。** 日期、时长、依赖顺序、护栏全部由 `engine.ts` 决定，LLM 只能：

- 写一段综述（`narrative`）
- 改写每条调整的理由（`reasons`，**taskId 必须来自引擎的建议**）
- 补充语义层面的提醒（`cautions`，例如学生笔记里透露的困难）
- 推荐协商选项（`recommendedOptions`，**kind 必须来自引擎已给出的选项**）

`validateAdvisorOutput` 会**逐条核对模型的每个引用**，对不上的一律丢弃并计数
（`dropped.reasons` / `dropped.options`），而不是报错。**模型幻觉再离谱也写不进学生的计划文件**——
最坏情况只是措辞降级回引擎原文。

`engineView(plan, report)` 是这条降级路径的实现，它同时就是比赛现场的兜底方案：
没配 Key、模型超时、校验失败，功能都不会整个消失。

### 7.1 `interview.nextTurn`

```ts
输入:  { profile: Partial<LearnerProfile>, asked: QuestionSpec[], lastAnswer?: Answer }
输出:  { done: false, question: QuestionSpec }
     | { done: true,  profile: LearnerProfile }

QuestionSpec = {
  id: string
  kind: 'single' | 'multi' | 'scale' | 'date' | 'dateRange' | 'text'
  prompt: string
  options?: { value: string; label: string }[]   // single/multi
  min?: number; max?: number                      // scale
  why?: string                                    // "为什么问这个"，显示在题面下方
}
```

**关键设计**：LLM 只输出**题目规格**，前端渲染成表单控件。**不做自由聊天。** 这样交互简洁、可控、好看，而且每一题的作答都是结构化数据，直接进 `LearnerProfile`。

约束：最多 8 题；每题必须有 `why`；已问过的话题不得重复。

> **实现时新增了 `dateRange`**（原方案只有单日 `date`）。
> 原因：「期中考试周」这类不可用时间必须**结构化**。原先它是一道自由文本题——
> 模型读得懂，但本地兜底读不懂，于是断网时系统又会把任务排进考试周，
> 正是 `Task.notBefore` 那次事故的翻版。**学生说过的约束必须能被规则层强制执行，
> 不能只有模型看得懂。**

### 7.2 `planner.draft`

```ts
输入:  LearnerProfile
输出:  { goal, constraints, competences[], milestones[], tasks[], resources[] }
       （不含 id / version / meta / history —— 由代码补齐并校验）
```

生成后必须过 `validatePlan`。**失败不重试整份计划，而是把校验错误回灌给 LLM 做定点修复**（最多 2 轮），这样比全量重生成稳定得多。

### 7.3 `advisor.proposeAdjustments`

```ts
输入:  { plan, drift: Drift[], newResources: Resource[] }
输出:  { adjustments: (AppliedAdjustment & { reason: string })[], narrative: string }
```

`narrative` 是给学生看的一段话。`reason` 是每条调整一句理由——**这是评委判断"真自适应"还是"套壳"的关键，必须每条都有**。

## 8. 工具调用

**刻意只做 2 个**，避免"通用 Agent"这个无底洞。

| 工具 | 实现 | 输出 |
|---|---|---|
| `search_resources(query, opts)` | **纯本地**：内置资料库 + 确定性加权匹配 | `Resource[]`，每条带 `verifiedAt` 和 `source` |
| `contest_feed()` | **真的发 HTTP**：Codeforces 公开接口（免费、无需密钥） | 即将开赛的场次，带真实开赛日 |

### 8.1 一条硬规则：编 URL 就是撒谎

模型的参数里记着一堆看起来像模像样的链接，其中相当一部分是死的。
而 `Resource.url` 是学生要**点开**的东西，点开是 404 比没有这条资源伤害大得多。
所以这一层的分工写死了：

- **哪些资源存在** —— 静态资料库决定（`packages/shared/src/tools/library.ts`），
  每一条的网址都实际发过请求验证
- **给谁推哪几条** —— `retrieve.ts` 的确定性打分决定，可测、可复现
- **模型完全不能新增资源**：`withToolResources` 会把模型自己写的 `resources` 全部丢掉，
  并把「丢了几条」作为 `droppedModelResources` 返回，写进给学生的说明里。
  悄悄删掉模型产出，和模型悄悄改掉学生的话是同一类错误

### 8.2 赛事：能实时拿的实时拿，拿不到的不许猜

蓝桥杯 / CCPC / ICPC 都只有官网页面，没有可依赖的接口。想拿确切日期就得爬页面，
而爬页面在现场断网或对方改版时立刻失效——更糟的是**会让人忍不住"估一个填上去"**。

所以分成两类，界面上必须能一眼区分：

| | 来源标识 | 卡片上的说法 |
|---|---|---|
| 实时抓的 | `codeforces.com/api` | 「今天校验 · 来自 codeforces.com/api」+ **实时**胶囊 |
| 内置清单 | `资料库快照@2026-10-19` | 「资料库快照 · 人工核对于 2026-10-19」 |
| 没有日期的官网入口 | `资料库快照@…`，`deadline: null` | 只给官网链接，**不显示倒计时** |

**「是不是实时抓的」只认 `LIVE_SOURCES` 里显式列出的来源**，
不许用「不是快照 ⇒ 是实时」去推断：那样演示夹具里一条来自「校内通知」的静态数据
也会被标成「实时」。这两件事是不同的判断。

### 8.3 演示时钟比真实日期快半个月，撞出了一处显示错误

实测：机器真实日期 `2026-10-04`，演示时钟 `2026-10-19`。
而倒计时是拿 `today` 算的，于是**真实世界里即将开赛的场次在演示时钟下全都成了
「已截止 12 天」**——一张写着"已截止"的赛事卡看起来就像程序坏了。

修法：`contest_feed` 判断「还没开赛」用**真实时钟**（这是实时接口语义上唯一正确的基准），
但开赛日**早于 `today` 时不给 `deadline`**。标题里那个日期照样在
（「… · 2026-10-07 开赛」），信息一点没少，只是不显示一个会误导人的倒计时。
真实用户手上 `today` 就是今天，两者一致，倒计时正常显示。

这一条只有真的把接口调通、并且拿演示时钟跑一遍才会发现。
`.dev/check-feed.mjs` 就是为此存在的——降级本身不报错，不主动测一次就看不出来。

### 8.4 `plan.attachResources` 为什么是一条命令而不是循环

一次检索可能要加进十来条资源、挂到好几个任务上。用 `resource.add` + `task.edit`
循环去写会产生**十几条 history、十几次快照**，而且中途失败会留下
「资源进来了但没挂到任务上」的半截状态——学生会看到一堆不知道给谁用的链接。

检索是一次动作，就应该是**一条历史、一次快照、要么全成要么全不成**。
这条命令还刻意做成幂等的：已有的资源 id 跳过、已有的挂载合并，
连点两次不报错也不产生重复条目。

## 9. 移动端 UI 规格

### 9.1 技术选型

| 用途 | 选型 | 备注 |
|---|---|---|
| 框架 | **Expo（托管工作流，不 eject）** | 当前稳定为 SDK 56，以官方为准 |
| 路由 | expo-router | 文件式路由，与 Web 心智一致 |
| 样式 | NativeWind（Tailwind 语法） | 与 Web 开发心智一致，降低切换成本 |
| 动画 | react-native-reanimated | Expo Go 内置支持，`Layout` 动画是重排观感的关键 |
| 状态 | zustand | 比 Redux 轻 |
| 手势/拖拽 | react-native-gesture-handler | Expo Go 内置 |
| 文件 | expo-file-system（**web 上退回 localStorage**） | **`.studyplan` 文件真实落盘**。解析/序列化用的 js-yaml 在 `packages/shared`，移动端不直接引 |
| 分享/导出 | expo-sharing | 把计划分享出去，答辩有实物 |
| 通知 | expo-notifications | 每日提醒，移动端独有加分项 |
| 本地缓存 | AsyncStorage | 见下方警告 |

> ⚠️ **不要用 MMKV**：它需要 dev build，会失去 Expo Go 的即时预览，得不偿失。AsyncStorage 对本项目的数据量绰绰有余。

### 9.2 四个屏幕

**① Onboarding 访谈流**（第一印象，必须漂亮）
- 一屏一题，卡片式，顶部细进度条
- 按 `QuestionSpec.kind` 渲染对应控件（单选/多选/滑块/日期/文本）
- 题面下方一行小字显示 `why`（"为什么问这个"）——这个细节很加分，体现产品思考
- 每屏可跳过；右下角一个明确的"继续"

**② 今日 / 计划主页**（学生待最久）
- 顶部：目标一句话（学生原话）+ 进度环
- 主体：本周时间轴（横向周条 + 纵向任务卡）
- 卡片上的直接操作：勾选完成、切状态（进行中/跳过/卡住）、改预估时长
- 右下角浮动按钮打开 AI 助手抽屉（可收起）

**③ 复盘协商页**（**核心亮点，必须做好**）
- 上：本期完成情况（完成率、负载自评、偏差列表）
- 中：**调整列表**，每条 = 一句理由 + 一句影响 + 接受/拒绝开关
- 下：目标协商区（可选选项卡片，每张标注对总时长的影响）
- 底部："应用 N 项调整" → 触发 `plan.applyAdjustments` → version +1
- 顶部版本号可点，进入版本历史并可回滚

**④ 资源 / 情报面板**
- 卡片列出资源，**每条显示 `verifiedAt` 和来源**
- 赛事卡片显示截止倒计时

**⑤ 文件**（实现时补的，原方案里没有）
- 直接显示设备上那份 `.studyplan` 的**原文**，而不是内存里重新序列化的结果
- 显示存储后端、路径、保存状态、版本快照列表
- 文件读不出来时**不覆盖**，给一个显式的「用当前计划覆盖文件」按钮
- 导出（Markdown / `.ics` / 复制文件内容）与演示模式开关，见 §9.11
- 演示用：一键重置回示例计划（示例本身就是可直接讲的状态，里面有超预估的任务）

**⑥ 版本历史**（`/history`，二级页，从文件页进）
- 每一版显示时间、任务数、已完成数、目标原话，可展开看当时的原始文件
- 回滚走命令层 `plan.restore`，行内两步确认，见 §9.11

> 为什么补第⑤屏：§14 的演示脚本里有一句「翻到 `.studyplan` 文件本体」，
> 而那句话是整个产品定位的物质证据。把它做成一个**标签页**而不是二级入口，
> 是为了答辩时一步就能点到。

### 9.3 让"漂亮"落地的具体动作

1. 一套主色 + 一套中性灰阶；圆角统一（如全用 20px）；间距用 4 的倍数
2. **深色模式**（比赛投影时更好看）
3. **只做三处动效**，做精：
   - 任务勾选 → 划掉 + 卡片收起（`Layout` 动画）
   - 重排 → 卡片位移动画（这一处最能体现"系统在思考"）
   - 进度数字滚动

   落地时的实际做法与验证方式见 **§9.10**。原计划里的 `Layout` 动画
   （指 Reanimated 的 `Layout`）没有采用：Reanimated 4 需要往 babel 配置里加
   worklets 插件，而本项目目前**没有 babel.config.js**，加它是为了三个动效
   引入一处会波及整个打包链的改动。改用 RN 自带的 `Animated` 与 `LayoutAnimation`。
4. 空状态 / 加载态 / 错误态都要设计（评委一定会点到空状态）
5. 全部屏幕在手机宽度（375pt）下检查一遍

### 9.4 实现现状（与 9.1 选型的差异）

实现时有几处偏离了 9.1 的选型，都是踩过坑之后的决定。记录在此，**避免文档和代码打架**——参赛文档里写着一个库里没有的东西，比不写更糟。

| 9.1 原计划 | 实际采用 | 原因 |
|---|---|---|
| NativeWind（Tailwind 语法） | `StyleSheet` + 设计令牌 `src/theme/tokens.ts` | 本项目已因 pnpm 单仓 + SDK 57 踩了三次构建配置坑，不愿再在 babel/metro 上叠一层；而且「漂亮」的关键在间距、层级、配色的**决策**，不在写 class 还是写对象 |
| zustand | React Context + `useReducer` | 状态只有一个 `plan` 加一条操作提示，reducer 足够；少一个依赖、少一个心智模型 |
| react-native-reanimated 动画 | 暂未使用 | 三处动效改用 RN 自带的 `Animated` 与 `LayoutAnimation` 实现了，见 §9.10、§9.11 |
| AsyncStorage | 暂未使用 | 移动端目前直接读夹具；落盘要等 `PlanStorage` 的移动端实现 |

另外几处**主动增加**的决定：

- **不用 `react-native-paper` 等 Material 库**：它渲染的是 Android 惯例（浮动按钮、涟漪、浮动标签），与「平台中立自有语言」的方向冲突。见 `.dsh/skills/expo-ios-hig/references/native-avoid-material-ui.md`。
- **不用图标库**：底部三个标签是两字中文，配药丸高亮已经足够；图标在这里是装饰不是信息，不值得为此引一个包。
- **不用 `react-native-svg`**：进度用线性条 + 大号数字，不为一个装饰元素引入原生依赖。
- **自绘勾选控件**（`CheckControl`）：RN 的 `Switch` 在 `react-native-web` 上不完全吃 `trackColor`/`thumbColor`，实机渲染成紫轨道配绿圆点；且它的语义是「设置项开关」，不是「采纳一条建议」。
- **测试用 `node --test`**：Vite 8 的依赖里 `child_process.exec('net use')` 在本机被 EPERM 拦下，故放弃 vitest。

**尚未实现**（对应 §2 的范围裁剪，不要误以为已具备）：

- AI 助手抽屉（浮动按钮）——演示脚本里没有这一环，优先级最低
- **本地通知**：判断是负收益。它要装 `expo-notifications`、走权限流程、还要平台配置，
  而**这一整套在当前环境下一次都验证不了**（没有设备，web 不支持）。
  为一个 3 分钟演示里不出现的功能去冒"可能把打包链搞坏"的风险，不值
- **原生存储没有在真机上验证过**：`expo-file-system` 那份实现是按 v57 文档写的、
  类型检查通过，端到端脚本验证的是 web 那份（localStorage）。
  开发机没有 Android SDK/adb，只能扫码上真机手动确认
- 重排位移那一处动效是原生专属（`LayoutAnimation` 在 react-native-web 上是空操作），
  截图和端到端脚本都证明不了它

### 9.5 实测数据（deepseek-flash，2026-10）

演示脚本给各段留的时间很紧，所以延迟是要盯的指标：

| 调用 | 实测耗时 | 备注 |
|---|---|---|
| `interview.nextTurn` | 1–5 秒/题 | 可接受，访谈本来就是交互式的 |
| `planner.draft` | **20–40 秒** | 演示脚本给这一段留 30 秒，**偏紧** |
| `advisor.proposeAdjustments` | 数秒–十几秒 | 输出短 |

`planner.draft` 慢的原因不是提示词，而是**输出长**：十几个任务、每个 6 个字段的 JSON。
最初的提示词里给了一个写满 12 个字段的示例，模型照抄，耗时一度超过 90 秒
（provider 默认超时 60 秒，`completeJson` 还会重试一次，最坏 120 秒）。
把示例改成最小形态、明确允许省略有默认值的字段之后降到 30 秒上下。

**移动端的超时必须按真实延迟定。** 最初把生成计划定成 30 秒，
结果是模型还在写、客户端已经放弃并**静默**回退到本机——
界面上只显示「计划已生成（本机）」，完全看不出是被超时掐掉的。
这是最难查的一类 bug：两条路都能跑通，只是跑了差的那条，而且不报错。
现在出题 25 秒 / 生成 90 秒 / 复盘 60 秒，宁可多等一会儿也不静默降级。

**演示时如果嫌慢**：把 `profile.weakSpots` 减到 1 项（任务数随之减半），
或者让那一段直接走本地生成（`useLlm: false`）——
本地路径是毫秒级的，代价是任务变成把「薄弱点」套进固定模板。

### 9.6 四条来自模型行为的教训

记在这里，因为**都不是类型检查或单测能发现的**：

**① 一个歧义短语就能让产品跑到别的领域上。**
系统提示词原来写的是「你是一个**中文学习规划助手**」。这句话有两种读法：
「中文·学习规划」（用中文做规划）和「中文学习·规划」（规划怎么学中文）。
模型选了后者，访谈第一题问出「**你学中文，主要想解决什么问题？**」。
改成「你是一个学习规划助手，用简体中文工作。你的服务对象是中国的大学生」之后正常。

**② 模型会照抄示例的"完整度"。**
上面的性能问题就是这么来的：示例里把 `Task` 的 12 个字段写全了，
模型就认为"输出应该长这样"，于是每个任务都写满——
而 zod 那边其实有默认值，省掉能快一倍以上。
**给模型的示例不是文档，是模板**，它会把示例的冗余当成要求。

**③ 模型会把学生原话"润色"掉。**
学生填的是「蓝桥杯省赛，目标是省一」，模型把它改写成
「用每周一 1 小时的固定时段冲刺 2026-11-18 的蓝桥杯省赛，以省一为目标，
把 C++ 基础语法、枚举模拟……练到能稳定拿分」。
读起来更专业，但复盘页要**原样回显**的就是那句话——那是学生三个月后还会回来看的东西。
提示词里已经写了「保留原话」，模型照样改。**这类不变量必须由代码强制**
（`assemblePlan` 里覆盖 `goal.statement` / `goal.deadline` / `constraints.blackouts`），
不能靠提示词自觉。

**④「返回 200」不等于「计划是对的」。**
端到端脚本因此用共享层的 `parsePlan` + `validatePlan` 独立复查一遍模型产出的计划，
并检查它是否真的遵守了学生说的可用星期与不可用区间。
只断言 HTTP 200，等于把「模型有没有听话」这件事交给运气。

### 9.7 一个靠 id 巧合维系的映射（已修）

这条值得单独记，因为它是**两个功能各自都"能跑"**、合起来却完全失效的典型。

最初 `QuestionSpec` 没有「这题的答案存到哪个档案字段」这个信息，
`applyAnswer` 靠**题目 id 猜**：只认 `q_goal` / `q_weekdays` 这些我们自己定的 id。

于是接上模型之后：
- 模型出的 id 是 `q_dp_focus` 之类 → 答案**一条都写不进档案**，访谈全程白做，
  而且没有任何报错，只是最后生成出一份通用计划；
- 模型若碰巧用了 `q_weekdays` 这个 id、但选项值是「工作日」→
  写进一个非法的 weekday → **档案非法** → 之后每一个 `/interview/next` 请求都 400，
  访谈当场死掉，而报错里看不出是哪一题写坏的。

修法是让映射显式化：`QuestionSpec.field` 声明目标字段，
`applyAnswer` 按 field 分派，写入前先用目标字段的 schema 校验一遍
（非法值整条丢弃——宁可少一条信息，也不能让档案变成非法值）。
`validateInterviewQuestion` 还会丢掉 **kind 与 field 不匹配**的题，
因为那种题的答案根本写不进去，问了等于没问。

### 9.8 两条来自「落盘」的坑

**① 持久化会把「只在一次会话里成立」的不变量变成跨会话的。**

演示时钟是一个内存游标，每次会话都从计划更新时间之后一分钟起步。
加了落盘之后，计划文件里的 `meta.updated` 会随会话一路前进，而重启后游标回到起点——
`applyCommand` 那条「命令时间早于 `meta.updated` 就拒绝」随即把**之后每一条命令**都挡下来。
表现是「打开还能看，一操作就没反应」，而且原因藏在一条 notice 里，很容易被当成 UI 卡了。

修法：从设备读回计划后立刻 `syncClockTo(plan.meta.updated)`。

这条不是设计缺陷，是**测试盲区**：单测每次都从干净状态起跑，永远遇不到
「上一轮会话把时间推到了未来」。抓到它的是端到端脚本里加的那一步「刷新页面再操作一次」。

**② 「有没有未落盘的改动」不能用版本号判断。**

重新生成计划时版本号会回到 v1。如果拿 `plan.version === lastSaved.version` 来判断脏，
「v1 → v1」这种改动会被当成没事发生，那次改动就**永远不落盘**，而且不报任何错。
改用单调递增的修订号。

两条的共同点：**落盘让状态多了一个维度（跨会话），而这个维度上的错误几乎都是静默的。**

### 9.9 仪表盘本身也要是真的

上真机之前先把「文件」页当仪表盘检查了一遍，发现两处会让它**说谎**的地方。
两条是同一类错误：**显示出来的结论不是从真相源读的，而是从"我刚做了什么"推的。**

**① 「已保存到设备」曾经是"我刚写下去了"，不是"盘上确实是这个"。**

`planText` 的定义写在文件头：「设备上那份文件的原文」。但代码原来是写入成功后
直接把它设成 `serializePlan(plan)` 的结果——也就是**刚序列化出来的字符串**，
根本没读过盘。后果是写盘如果静默失效（写空、写错位置、原生模块吃掉了内容），
界面照样显示正确的正文和「已保存到设备」，是**一次假通过**。

修法：每次写完立刻 `readPlan` 读回来，和写下去的逐字符比对，不一致就报错并保持
`planText` 不变。宁可显示失败，也不显示一个假的成功。
落盘这件事上，**唯一有说服力的证据是读回来的东西**。

**② 「读不出来」曾经只有一种，而两种的处理方式相反。**

文件内容不合法（多半是手改敲错）和存储本身坏掉，原来会走到同一个 catch、
显示同一句「读取存储失败」，并且都给「已暂停写入以免覆盖你的修改」和
「用当前计划覆盖文件」按钮。可是存储坏掉时覆盖按钮**没有用**——写不进去，
真正该给的是重试。真机排查时这句错话会把人引去查格式，而问题在存储层。

修法：`loadError` 带 `kind`。`parse` 走「不覆盖 + 覆盖按钮」，
`io` 走「存储不可用 + 重试按钮」，并说清后果（计划只在内存里）。

**顺带修掉的一个必然后果**：有了重试就必须在重试前解除写入封锁，
否则学生按提示把文件改好、点了重试，`blocked` 还是 true，仍然写不进去。

### 9.10 三处动效的实际做法

不用 Reanimated（理由见 §9.3），全部用 RN 自带的 `Animated` 与 `LayoutAnimation`。
时长与曲线统一取自 `theme/tokens.ts` 的 `motion` / `easeOut`，
组件里不许各写各的——第一次微调就会漂移出四五种手感。

| 动效 | 做法 | 是否只动 transform/opacity |
|---|---|---|
| 勾选 | 20pt 方框上**盖一层实心填充淡入**，勾号同时 0.6→1 缩放 | 是 |
| 划掉 | 见下 | 是 |
| 卡片收起 | 量出内容真实高度，动到那个高度；收起动画播完才卸载子树 | **否**（高度） |
| 进度数字 | 从**当前显示值**滚到新值 | **否**（文字内容） |
| 重排位移 | `LayoutAnimation`，**原生专属** | 否 |

`motion` 那条「只动 transform 与 opacity」的规则因此不是绝对的，
两处例外都在各自文件里写了理由，`tokens.ts` 的注释里也点了名。

**划掉为什么是「第二份文字」而不是画一条线。**

划过标题的那条线是**第二份一模一样的文字**，只是 `color: transparent`
而 `textDecorationColor` 用真实颜色，于是只有线可见；再把这个副本整体淡入。

- 自己画线：标题经常折成两行，按容器宽度画的线会一直伸到第二行末尾的空白处
- 去量文字：`onTextLayout` 在 react-native-web 上是空的，而截图与端到端脚本
  都跑在 web 上——量出来的东西在两边会不一致，等于给自己造了一个只在真机上
  出现的差异

代价是同一句话在 DOM 里出现两次，所以副本必须 `aria-hidden`。
注意**只写 `aria-hidden`**：RN 自己会把它翻成原生的 `accessibilityElementsHidden`，
而 react-native-web 不认后者、会当成未知属性报 console 警告（端到端脚本因此会红）。

**验证方式：不能靠静态截图。**

静态截图只拍得到动画的终点，而终点和「压根没有动画」长得一模一样。
所以新增了 `.dev/motion.mjs`：在动画**进行中**取样，断言

1. 划线副本文字透明、装饰线有色、未勾选时 opacity 为 0，勾选后 70ms 严格落在 0 与 1 之间；
2. 面板展开 60ms 时的高度严格小于终态高度；
3. 取消勾选后，已投入分钟数在 60ms 采到区间**内部**的值（实测 25 → 7 → 1 → 0）。

第 3 条刻意选区间大的那次变化：从 1 掉到 0 这种区间为 1 的滚动，
中途值只可能是两个端点，「在滚」和「瞬间跳」根本区分不出来。

### 9.11 导出与版本回滚

#### 导出为什么不是加分项

`.studyplan` 是自定义格式，这是产品的卖点。但自定义格式有一个天然风险：
**它变成数据孤岛**——学生没法把它带进日历，也没法贴给同学。
所以导出是让"自定义格式"这个选择站得住脚的必要条件，不是锦上添花。

**生成与投递分开**：`packages/shared/src/plan/export.ts` 只生成字符串，
不碰文件系统；真正写文件和调分享面板在 App 侧按平台分文件。这样生成器能被
23 项测试逐条盯住——而且必须盯住，因为**这两种格式写错的表现极难定位**：
ICS 写错了，日历只说"这个文件打不开"，不会告诉你哪一行有问题。

#### ICS 里踩到的几条（都写进了测试）

1. **必须 CRLF**（RFC 5545）。用 `\n` 的文件有些客户端直接拒收。
2. **折行按 75 字节，不是 75 字符**，而且不能把一个多字节字符切成两半。
   中文一个字 3 字节，一折行就踩；**用英文测试数据永远发现不了这个 bug**。
   实现里按字符逐个累加字节数，所以天然不会切断字符；测试则反过来验：
   拼回去必须和原值逐字符相等，且不能出现 `\uFFFD`。
3. **全天事件的 `DTEND` 是"次日"**——ICS 里它是**开区间**。写成同一天会变成
   零长度事件，很多客户端干脆不显示。
4. **UID 要稳定**（`planId-taskId`），否则每次导出都是新事件，导入两次就有两份。
   `SEQUENCE` 直接用计划版本号，客户端据此知道这是更新。
5. 值的转义顺序要紧：`\` 必须最先替换，否则会把后面转义出来的反斜杠再转一遍。

**为什么是全天事件而不是"周三 19:00–20:30"**：`Task` 里只有
`scheduledFor`（日期），**没有开始时刻**。拿 `constraints.availableSlots` 里那个时段
去凑一个开始时间看着更漂亮，但那是在**替学生编一个他没说过的时间点**——
他填的是"周三晚上有空"，不是"这件 45 分钟的事从 19:00 开始"。
日历上摆错时间比摆一整天更烦人。

#### 回滚的两步确认

快照一直在写、命令层的 `plan.restore` 也早就可用，但**界面上一直没有入口**——
一个学生永远点不到的功能，和没做是一样的。

回滚做成行内两步（先点「回滚到这一版」，按钮变成「确认回滚到 v3」，再点才执行），
而不是弹 `Alert`：`Alert` 在 react-native-web 上没有实现，而且回滚虽然可逆
（回滚前那一版同样会被快照下来），它毕竟是把学生**看得见的**进度换掉。

端到端脚本对这一步的断言不是"版本号变了"，而是**内容真的回到了旧版本**：
拿资源条数做判据（找资料发生在 v1 之后），实测 `资源卡 7 → 4`。
只看版本号的话，"回滚命令执行了但内容没换"这种错会被漏过去。

#### 演示模式防的不是断网

`lib/demo-mode.ts` 打开后一次网络请求都不发。它防的**不是**断网——
这个 App 每条 AI 路径都有本机兜底，断网会立刻失败并在几毫秒内退回本机，那是安全的。

会出事的是相反的情况：**场地 Wi-Fi 通着，但模型 API 连不上**（被墙、额度用完、服务抖动）。
这时请求不会立刻失败，而是一路等到超时，而生成计划那条的超时是 **90 秒**。
台上站着等 90 秒，比"它答得不好"严重得多。

用模块级标志 + `useSyncExternalStore` 而不是 React state：消费它的是
`lib/api.ts`——一个纯模块，拿不到 context。

### 9.12 两条只有真机才暴露出来的教训

真机上跑出来的第一个报错是：

```
Encountered two children with the same key, `赛事缺少截止日期，无法显示倒计时`
```

复盘页的「提醒」列表当时写的是 `key={c}`——**拿警告文案当 React 键**。
顺着它挖下去，发现真正的问题不在这行代码。

#### ① 键不能建立在「文案不会重复」这种假设上

那条被撞的警告来自一条校验规则：**每个没有截止日的赛事各报一次**
「赛事缺少截止日期，无法显示倒计时」。文案是按规则写死的，所以几个赛事就几条
**一模一样**的字符串——键必然重复。

`path` 是结构性的（`resource:xxx` / `task:xxx`），它才该是键。
现在键写成 `fmt:${path}`，引擎那一路用 `engine:${i}` 加命名空间——
两个来源互不知道对方的内容，用同样的字符串做键迟早会撞。

**文案是给人看的，随时可能为了更好懂而被改成一样的。** 键不能依赖它。

#### ② 校验器不该对「我们有意为之的状态」报警

删掉键的重复还不够——那一列会显示三条一模一样的提醒，而它们说的是一件
**我们故意做的事**。

工具调用上线之后，「赛事没有截止日」变成了正常状态：蓝桥杯 / CCPC / ICPC
只有官网、没有可靠日期，我们**拒绝编一个**；演示时钟下实时抓来的场次同理
（见 §8.3）。于是每份生成的计划都带 3–7 条关于「我们有意不做的事」的警告，
把真正需要注意的事淹掉了。

`validatePlan` 该报的是**计划里的自相矛盾**，不是「某个字段我们选择留空」。
规则删了，信息挪到了它该在的地方——资源卡上写「未记录截止日 · 以官网为准」，
学生点开那条资源时正好看到。

这条测试钉住了「别再把它加回来」，`schema.ts` 里也留了一段注释说明为什么删。

#### 顺手清掉的一处死代码

`store.warnings` 被 `apply` / `installPlan` 填上，但**从来没有任何界面读它**——
复盘页是直接对 `plan` 重新跑 `validatePlan` 拿警告的。同一件事算两遍、其中一份
没人用，是纯粹的分歧风险（哪天两边口径不同，谁也不会发现）。删了。

#### 验证方式

这个错只在**连着服务端**时出现（离线路径不会带进没有截止日的赛事），
所以只跑本机路径的端到端是验不到的。改成两条都跑：

| 路径 | 覆盖什么 |
|---|---|
| `node .dev/flow.mjs` | 本机兜底、落盘、导出、回滚、演示模式 |
| 连服务端那条（临时 `.env` + `--dist apps/mobile/dist-live`） | **实时赛程 → 没有截止日的赛事 → 复盘页提醒区** |

跑完两条都是「无 console/page 错误」。顺带一提，第一次去跑时发现 8787 上
**还挂着上一个服务端**（更早的代码）——它拒绝启动而不是静默用旧代码服务，
这才没让验证落在错的东西上。README 的坑表里那条「端口被占用」说的就是它。

### 9.13 时钟：一个事实有四个来源，就一定会不一致

第二轮的需求是「时间应该由后端在后端所在的机器上获取」。查下去发现，
当时「今天」在项目里有**四个**来源：

| 位置 | 是什么 |
|---|---|
| `apps/mobile/src/state/clock.ts` | 一个写死的常量 `DEMO_TODAY = '2026-10-19'` |
| `apps/server/src/routes/plan.ts` | 一份 `todayLocal()` + 一份 `nowStamp()` |
| `apps/server/src/routes/interview.ts` | 又抄了一份 `nowStamp()` |
| `apps/server/src/tools/codeforces.ts` | 直接读 `Date.now()` |

它们不只是重复，而是**真的打过一次架**：演示日期是 2026-10-19，
实时赛程却按真实的 2026-10-04 过滤，于是抓回来的每一场在界面上都渲染成
「已截止 12 天」——一张写着「已截止」的赛事卡看起来就像程序坏了。
§8.3 记了当时的处理：在标题里保留日期、抑制倒计时。
**那是绕过，不是修复。**

这一轮把它收敛成一处：服务端 `clock.ts` 是全服务唯一的「现在」，
客户端只做纯算术（把 `offsetMinutes` 手工加到 epoch 毫秒上），
**永不自己做「UTC 时刻 → 本地日期」的换算**。

#### ① 那条「命令时间早于 meta.updated 就拒绝」的规则必须删掉，而不是修补

它的目的是防乱序写入把版本号推回去，代价是逼着「命令时间」真实递增——
于是必须养一个假时钟（从示例计划时间戳起步的单调游标），
因为示例计划的时间是演示口径、真实系统时间早于它，**每条命令都会被挡掉**，
界面表现就是「点了没反应」，而且看不出原因。

而**现在没有任何地方需要它**：客户端 `apply` 是同步 reducer，两条命令不可能并发；
服务端生成的计划走 `installPlan` 直接替换整份计划，**根本不经过命令层**。

所以是删掉，而不是换一个「命令带期望版本号」的替代品——
当前架构里没有第二个写者，加了就是一个永远不会被触发的字段，
而永远不会被触发的代码最容易腐烂。删掉之后 `cmd.at` 变成一个纯信息性字段，
**允许不单调**（调试模式回拨日期时它就该倒退，它是逻辑时钟不是墙上时钟）。

#### ② 顺着这条线发现了一个真的乱序写

生成一份计划要 20–40 秒。学生在这期间打勾、改时长，`installPlan` 回来时
会**静默覆盖**掉那些修改。这才是真正需要防的那个乱序写，而且它一直存在。
现在会比对修订号（发起生成那一刻 vs 现在），不一致就拒绝装入并说明原因。

#### ③ `Codeforces` 里的 `Date.now()` 是那个矛盾的直接来源

它和调用方传进来的 `today` 在同一个请求里共存。统一时钟之后
`nowMs` 也由调用方传进来，两个来源变成同一个。

#### ④ 时区错一天只在特定的 UTC 时刻暴露

`toISOString().slice(0, 10)` 是 UTC 的日期，东八区晚上 8 点之后会算成「明天」。
所以服务端时钟留了一个注入真实时刻的口子（`createServerClock({ now })`），
专门让这些时刻可以被测到——不给注入点就只能靠「跑到那个点再测」，那等于没测。
`time.test.ts` 里有一条测试直接用 `2026-10-19T23:30:00Z` 钉住它。

#### ⑤ 模型不许改数字：从口号变成约束

补账那一屏要对学生说「这 5 天里有 9 项没打勾」。数字数错是这一屏唯一不能犯的错，
而模型数数不可靠。

光在提示词里写「不要改数字」**没有约束力**——模型仍然会把 9 项说成 3 项，
而学生无从发现，他会因此对整个系统失去信任。所以约束落在校验上：
服务端拿白名单核对模型写出的**每一个整数**，出现白名单之外的就整段退回本机叙述。

一个必须处理的副作用：模型很自然会写「10 月 15 日到 10 月 19 日」，
那些数字是日期的组成部分，不是它自己算出来的计数。所以提取前先把日期整段挖掉，
否则每一句提到日期的正常叙述都会被判成「编数字」，这个功能就形同虚设。

#### ⑥ 一个只有实际点过才会发现的坑：调试模式下的「今天」是空的

文件页有一个〔今天〕快捷档位，本意是「回到今天」。第一版读的是 store 的 `today`
——而在调试模式下 `today` **就是被固定的那个日期**。所以学生把日期设到 12 月 25 日
之后，点「今天」得到的是 12 月 25 日：一个原地打转的空操作。

修法是 store 额外暴露一个 `realToday`（按设备时钟算），快捷档位读它。
端到端脚本一开始也是被这个坑住的：它填了 2026-12-25 再点「今天」，
之后「模拟隔了 5 天」的窗口就落在了一个没有任何任务的区间里。

#### ⑦ 重复犯的错：小字号的浅色文本当操作

§9.13⑦ 这条其实是**重犯**。任务卡上的「调整」按钮是一个 26×22 的
`textFaint` 文本，触控区远小于自己定的 `touchTarget = 44`，
而且从来没被任何测试点过（端到端脚本是靠「打勾自动展开」到达那一屏的）。
查清楚之后，我在新写的结账页上又写了一个一模一样的「这一项我不做了」淡色小字……

判据很简单：**如果一个操作看不出来能点，那它和坏掉没有区别。**
可以点的东西一律用胶囊或按钮，并且真的满足 44；纯文本只用来陈述。

### 9.14 日历与任务编辑（v0.3）

**① 两个视图说同一件事，就必须是同一个组件。**

「日历的格子和首页周条长得一样」如果靠两段 JSX 各自维持，迟早会长歪。
所以格子抽成了 `components/day-cell.tsx`，周条和月历都渲染它，
差别只有「周几」那一行（周条有、月历由列头承担）。

**连负载条的满格基准（`LOAD_FULL_AT`）也同源**，这一点比配色更要紧：
两个视图如果对「多重算满」理解不同，同一个学生在同一天会看到两种长度，
而**长度是这一屏唯一的信息载体**（颜色已经被状态占用了）。

抽取的安全性不是靠看：`.dev/shot.mjs` 按语义定位周条的七个格子并裁一张图，
改动前后 **SHA256 逐字节相同**。

**② 月历固定 6 行（42 格）。** 不做「够用就少一行」——行数一变整屏高度就跳，
而学生在日历上做的就是前后翻月份。周起始日是周一（与「本周」同口径）。

**③ 「点 = 展开、长按 = 编辑」不会互相误触发**，因为
react-native-web 的 `PressResponder` 里长按之后不调 `onPress`
（`isPressCanceledByLongPress`），原生端 `Pressability` 同规则。
但**勾选框必须是可点区的兄弟而不是子元素**：`Pressable` 套 `Pressable`
在 web 上点击会冒泡、在原生上靠 responder 系统，两边行为不一致。
这条在 e2e 里是显式断言的（长按后「处于展开状态的卡片」必须是 0 个）。

**④ 长按不能是唯一入口。** 对读屏用户它完全不可见，
所以展开区第一行仍然有一个「编辑这一项」的胶囊。

**⑤ 编辑页：除标题和备注外没有一个自由文本输入。**
日期点月历（和日历屏同一个 `CalendarPanel`）、时长用档位 + `±15`、
类型/标记/前置/资料全是点选。理由不是审美：手打日期要求学生在脑子里做格式转换，
而旁边就有一张月历；而且**点格子不可能点出一个不存在的日期**。

「最早可安排日」复用**同一张月历**，上面一个「正在设定：排期 / 最早可安排日」的开关
决定写进哪个字段——一张月历 + 一个开关，比两个分开的控件好理解，
也少了一个要单独校验的输入。

**⑥ 一次保存 = 一条命令。** 取消版本管理之后这一条**变得更硬**了：
拆成四条的话，中间任何一条被拒（字段非法、前置成环）都会让前面几条已经生效，
而**现在没有回滚能把这一次编辑整体撤掉**——学生看到的是「标题改了、日期没改」。
次要理由：一次编辑在 history 里变成四行；一次编辑打四遍写盘和四份快照。

**⑦ 顺手修掉一个潜伏的洞。** `task.edit` 原本只有 `Object.assign(t, cmd.patch)`，
没有任何字段校验，而 `validatePlan` 不管字段合法性。于是 `title: ''`
会 `ok: true` 地写进磁盘，**下一次启动解析就失败**，界面进入暂停写入的保护状态。
它之前踩不到，只因为**没有任何界面调用 `task.edit`**——编辑页是第一个调用者。
现在走整条 `Task.safeParse`，一次覆盖全部字段。

**⑧ 标记存 id，不存文字。** `task.tags: ['tag_focus']`，目录在 `plan/tags.ts`。
以后要加「时间标记（影响排期）」或「自定义颜色」，改的是目录和引擎，
**任务上的数据一个字都不用动**。这就是框架，而它是靠**引用方式**建立的，
不是靠预留空字段——`kind` / `payload` 这类今天没人读的字段**故意没有加**。

格式改动是 `.default([])`，所以 `SCHEMA_ID` 不动、旧文件照常解析。
这一点有专门的用例盯着（`describe('格式演进：只加可选字段')`，
而且刻意用手写的旧文件当样本，不用示例文件——那份文件以后可能被补上 tags）。

**⑨ 移动端的「尽量别引依赖」也适用于工具链。** HMR 探针用 Node 22 自带的
全局 `WebSocket`，不装任何东西。

### 9.15 复盘与「跟 AI 说说」（v0.4）

**① 事实在前，建议在后，而且事实不过模型。**

复盘一屏六块（事实 / 问答 / 方向 / 卡片 / 现在的安排 / 复盘日志），顺序是刻意的：
「通读核心概念实际花了预估的 2.18 倍」这句是本机算的，**模型碰不到**。
先有事实再有建议，学生才有可能不同意建议；反过来先给建议，
事实就变成了建议的论据，那一段就没有可争的地方了。

事实既然不过模型，它就可以**先显示**——不用在白屏上等一次模型调用。

**② 建议是「方向 + 帮你写好的卡片」，卡片是例子，不是命令。**

先给方向（「下周 1 项换个日子、1 项时长调一下」），再递上具体的卡片。
每张卡可勾掉、可划掉、可点进去改成学生自己想要的样子。

**不设条数上限**。原来的「最多 5 张」是错的：上限只会砍掉最后几条，
而学生不知道少了什么；宁可多给一张让他划掉。

**③ 编辑建议卡必须预填「建议值」，不是「当前值」。**

这是这一版最容易做错、又最难在截图上看出来的一条：做错了界面完全正常，
只是每张卡点进去都变成个没改动的表单——「帮你写好」这件事一点都没发生。
`/task/[id]?proposal=<key>` 复用同一个编辑页，预填的是提案里的值，
存回去走 `editProposal` 写回会话（不是直接落盘）。
端到端里有一条**专门盯着预填值**的断言。

**④ 一个 `Proposal` 类型，两处产出，一条命令。**

复盘（本机规则）和「跟 AI 说说」（模型）产出的是**同一个联合类型**，
应用时走**同一条** `plan.applyAdjustments`。两条路各写一套的话，
「复盘能改的东西」和「跟 AI 能改的东西」迟早不一样，而且第一处迟早忘记加校验。

模型的输出是 `z.unknown()` 收的，进 `validateProposal(plan, today)` 逐个把关：
编出来的 id、过去的日期、撞上不可用区间的日期、越界的时长，全部拒掉，
**理由要是人话**（它会原样显示给学生）。

**⑤ 澄清轮数必须有上限，而且上限要排在「有问题就不给提案」之前。**

真机上发现模型会**连着问第二个问题、一个提案都不给**，学生就卡在澄清里出不来。
`MAX_CLARIFY_ROUNDS = 2` 修掉它——但第一版修错了顺序：先判「有 questions 就不看 proposals」，
再判轮数上限，于是模型**同时**给一个问题和一个提案时，两样都被丢掉。
上限必须先跑（测试抓到的，不是我想到的）。

同一个坑的另一面：`TalkOutput.questions` 的 schema 上限定成 2，
模型回三个问题时**整份输出解析失败**，一条澄清都显示不出来。
现在 schema 放宽到 4、由 `resolveTalkOutput` 截断——**schema 负责能不能解析，
业务规则负责留几个**，混在一起就会把一次小越界升级成彻底失败。

**⑥ 做不到的要明说（`refusals`），断网就不假装在工作。**

「让 AI 改不可用日期」这类越界请求会返回一条明确的拒绝和原因，不是静默忽略、
也不是改个别的来充数。断网时 `/talk` 直接说「现在用不了」并把手动入口（日历）摆在旁边，
**没有做关键词兜底解析**——那种「看起来在工作」的假成功比直接说不能更坏。

`/talk` 是全项目**唯一没有本地 fallback 的 LLM 路径**（其他每条都有），
因为它的全部价值就是「听懂一句自然语言」，本地规则听不懂还硬答，是在骗人。

**⑦ 撤销只活到下一次改动之前。**

撤销不是反向再发一条命令，而是 `plan.restore` 装回应用前的快照。
**任何一次新的改动都会清掉 `undoSnapshot`**——留着旧快照的话，
学生会把中间那次改动一起撤掉，而那不是他要的。
撤销本身也走命令层、也是一次正常写入（版本 +1），因为它确实改变了计划。

**⑧ 档案住在计划文件里，而它的界面镜像必须每次都从计划重新读。**

`plan.profile` 是「它记得你说过的话」唯一站得住的实现：重开 App 还在、
换设备跟着走、「跟 AI 说说」有依据。

这一版真正修掉的是一类**「两份真相」的漂移**：档案既在 `plan.profile` 里、
又在 store 的 `state.profile`（界面读它）里，于是有两处各自维护它——

- `installPlan` 不传档案时原来写的是「保持原样」，**错**：
  从文件页一按「重置为示例计划」，计划里明明有档案，镜像却还是旧的（常是 null），
  页面显示「还没有档案」而正下方文件正文里就写着档案；
- `apply` 之后**完全不更新**镜像，于是「我每周只有 3 小时了」改到了文件，
  界面还显示旧值，下一次对话拿着过期档案去回话。

现在两处都是 `readProfile(plan)` 重新读。一次 `safeParse` 的代价换掉一整类漂移。
同理，`withProfile` 里的数组要**逐层复制**，浅拷贝会让计划和镜像共用同一个
`weekSpots` 数组——镜像上一改，计划对象跟着悄悄变了，而它没走过「改 → 校验 → 写盘」。

**⑨ 会话的「今天」必须在时钟就绪之后才准开，而且不能只靠这个。**

这一版唯一一次**真的差点出事**的 bug：复盘会话是用一个过期的「今天」建的
（时钟还没连上，用的是设备日期），于是卡片把 10/21 的任务「挪」到了 10/14——
一张过去的日期，应用下去等于把任务挪进历史。

两道闸：`startReview()` 等 `storageReady` 才准开；`reviewProposals()` 出来的每一张卡
**再过一遍 `validateProposal`**，任何一张不过就当场丢掉而不是渲染出来。
两道都要——第一道是时序依赖，很容易被下一次改动破坏；第二道是不变量。

**⑩ 入口组件与位置解耦。**

`<ReviewEntry />` + `useReviewLauncher()`、`<TalkEntry />` + `useTalkLauncher()`：
组件不假设自己在哪一屏的哪个角，要挪位置只改一行 JSX。
手动触发和（将来的）主动提示共用**同一个** `openReview()`——
不写没人调用的函数，也不为了「以后可能主动提示」现在就堆条件判断。

**⑪ 一个永远读不到的断言不是检查。**

端到端里原来有一条读「版本快照 · N 个」的断言。版本管理界面在 v0.2 就撤掉了，
所以它几个月来一直静静地记 `(没读到)`，既不会失败也不会提醒任何人。
这一版换成拿**页头的版本号**和**文件正文里的 `version:`** 对一次——
两处对得上，才说明这一页显示的确实是盘上那份文件。

同一条道理适用于验收：**「界面显示了这句话」不等于「这句话来自文件」**。
档案那一条断言读的是人话摘要（「每周约 3 小时」），而文件正文里只有
`weeklyHours: 3`——所以它只可能来自 `readProfile(plan)`，不可能碰巧通过。

```
├─ pnpm-workspace.yaml
├─ packages/shared/            ← 唯一真相源，无平台依赖

└─ docs/技术方案.md            ← 本文件
```

### ✅ 已排除的风险：Metro + pnpm workspace（原判断有误）

**原方案预留了 2 小时止损，实测不需要。** [Expo 官方 monorepo 文档](https://docs.expo.dev/guides/monorepos/)明确：

- **SDK 52 起 `expo/metro-config` 自动处理 monorepo**。如果 `metro.config.js` 里出现 `watchFolders`、`resolver.nodeModulesPath`、`resolver.extraNodeModules`、`resolver.disableHierarchicalLookup`，**要删掉**，然后 `npx expo start --clear` 清一次缓存。
- pnpm 默认的 isolated 安装策略自 **SDK 54** 起受支持；若遇到原生构建或解析错误，在 `pnpm-workspace.yaml` 加一行 `nodeLinker: hoisted` 即可回退。
- **SDK 55 起**，monorepo 中的 app 自动启用 `experiments.autolinkingModuleResolution`。

需要自己盯的只剩一条：**重复的 React / React Native / 原生模块版本**。用 `pnpm why --depth=10 react-native` 检查，必要时在根 `package.json` 用 `pnpm.overrides` 强制统一。

## 11. 迭代加速设施（直接对应第 1 节）

这一节是本方案能省下大量时间的**真正原因**，不是"锦上添花"，请优先做。

| 设施 | 作用 | 成本 |
|---|---|---|
| **浏览器优先开发** | UI 迭代在浏览器 HMR 完成，真机只做验收 | 配置成本极低 |
| **场景切换器（dev panel）** | 一键跳到任意状态，省掉每轮的导航时间；三人可同时试不同状态 | 半天 |
| **场景夹具 `scenarios/*.studyplan`** | 空计划 / 超载 / 第 3 周复盘 / 里程碑危机 / LLM 失败 | 1 小时 |
| **Mock 模式** | `MOCK=1` 时后端返回固定 fixture，响应毫秒级且可复现 | 2 小时 |
| **组件画廊屏** | 把所有组件的所有状态堆在一屏，一次看完全部视觉问题 | 1 小时 |
| **纯函数单测** | AI 自证逻辑正确，人类不需要读这部分代码 | AI 生成 |

**其中 Mock 模式同时是比赛现场的兜底**：网络或 API 出问题时一键切换，流程照跑。

## 12. 排期（按人类循环数）

假设 2–3 人，每天 2–3 小时，总预算约 106 人时。

| 阶段 | 内容 | 人类循环数 × 每轮 | 小计 |
|---|---|---|---|
| **P0** | 环境 + 脚手架（已验证：工作区、依赖、typecheck、测试全绿） | 4–6 × 10 min | 0.7–1 h |
| **P1** | 内核（schema / 命令层 / 校验 / 引擎 + 单测） | 5–8 × 10 min | 1–1.5 h |
| **P2** | 视觉与交互（4 屏 × 6–12 轮视觉迭代） | 24–48 × 6–10 min | 3–6 h |
| **P3** | 端到端联调（LLM 接入、真实流程跑通） | 25–40 × 6–12 min | 3–6 h |
| **P4** | **产品试用与调整** | 3–5 名学生试用 + 3–6 轮改版 | 4–8 h |
| **P5** | 演示打磨 + 兜底 + 录屏 | — | 2–4 h |
| | **合计** | | **≈ 15–28 人时** |

**关键结论：预算有 3–5 倍冗余。省下来的时间全部投给 P4。** 多找几个真实学生试用，比多加三个功能有价值得多。

### 并行建议

- **P0/P1 由 1 人主攻**（且必须最先完成），其他人同期做视觉设计稿与文案
- **P2 可拆**：一人负责访谈流 + 计划页，一人负责复盘页 + 资源页
- **P4 全员参与**，且必须找**队伍之外的真实学生**试用

## 13. 风险与兜底

| 风险 | 影响 | 对策 |
|---|---|---|
| Metro + pnpm 配置 | 时间黑洞 | 2 小时止损，降级为复制式共享（见 §10） |
| 依赖需要 dev build | 失去 Expo Go 即时预览 | 只用 Expo Go 支持的库；不用 MMKV |
| 现场网络 / API 故障 | 演示当场挂 | **Mock 模式 + 提前录屏** |
| 自定义格式成数据孤岛 | 学生不带走来用 | P5 前加导出 md / ICS（成本几小时） |
| AI 生成的 UI 趋于平庸 | "漂亮"这条硬要求不达标 | 人工打磨 §9.3 的三处动效与配色 |
| 用真名/真实学情数据 | 隐私问题 | 演示数据全部虚构；本机存储 |

### 13.1 已决定但押后：设备端直连（BYOK）

**问题**：现在 App 通过服务端调模型，于是「给别人用」就等于「我们得提供云服务」——
要养服务器、要保管密钥、要扛费用。

**结论：不必。后端在这里基本只是个壳。**

`packages/llm-client` 只依赖 `zod`，而且当初就是按「能在 Hermes 上跑」写的
（`openai.ts` 特意手写超时，注释写明 `AbortSignal.timeout` 在 Hermes 上不保证存在）。
React Native 需要的东西全都自带——`react-native/Libraries/Core/setUpXHR.js` 里
polyfill 了 `fetch` / `Headers` / `Request` / `Response` / `AbortController` / `AbortSignal`。
服务端的真实职责只有两件：**保管密钥**和**提供 fetch**。后者手机自带；
前者换成「用户自己的密钥」就不需要保管了。

**一条硬约束：绝不能把我们自己的 key 打进安装包。** 反编译就能抠出来，
别人拿去烧我们的余额。所以设备端直连只能是 **BYOK（用户自带密钥）**，
密钥存 `expo-secure-store`（Keychain / Keystore），不能进 localStorage / AsyncStorage。

要做的事：

| | 工作 | 说明 |
|---|---|---|
| 1 | 抽出 `packages/agent` | 把 `apps/server/src/routes/interview.ts` 里约 70 行「提示词 → 调用 → 校验 → 定点修复 → 本地兜底」从 Fastify handler 搬到 `provider \| null` 参数化的纯编排，服务端与 App 共用。**主要工作量，且是纯搬运** |
| 2 | App 加设置页 | baseUrl / apiKey / model |
| 3 | `api.ts` 加第三条路 | 有 key → 本机直连；没 key → 有服务端就走服务端；都没有 → 本地兜底（已有） |
| 4 | 改 `llm-client/src/index.ts` 的头注释 | 它现在写着「注意移动端**不**使用这个包」，届时就不成立了 |

**收益不只是省掉云服务**：数据不出设备（计划文件本来就在本地）、
兼容任意 OpenAI 端点（DeepSeek / Kimi / 校内 vLLM）、离线可用已有。

**服务端留着做两件事**：比赛演示（评委手机上不会有 key）、
将来需要服务端密钥的工具调用（赛事信息抓取）——那是唯一真正必须服务端的。

**一个运行期注意点**：生成计划要 20–40 秒，得保持前台；
iOS 切到后台会掐掉请求。现在的服务端方案在客户端看来同样有这个约束，不是新增风险。

**为什么押后**：它决定的是**演示形态**（要不要一台笔记本），不是某个功能的好坏。
按当前优先级先做完动效与流程，等第一个版本齐了再动它——那时改动的成本不会变高，
因为第 1 步是纯搬运。

## 14. 演示脚本（3 分钟）

| 时间 | 内容 | 要点 |
|---|---|---|
| 0:00–0:20 | 问题陈述 | 「学生不缺资料，缺的是把资料变成可执行计划的闭环」 |
| 0:20–1:00 | 现场跑 Onboarding 访谈 | 展示 LLM **动态出题**且渲染成表单，不是聊天框 |
| 1:00–1:30 | 生成计划，**翻到 `.studyplan` 文件本体** | 强调：这是自定义格式，可读、可手改、可导出 |
| 1:30–2:10 | 打勾两项 + 手改一项时长 → 触发重排 | 卡片位移动效；展示系统识别出"超前/落后" |
| 2:10–2:40 | 复盘协商页 | **逐条理由 + 接受/拒绝** ← 全场最关键的 30 秒 |
| 2:40–3:00 | 工具调用拉到一场比赛并插入计划 | 指着 `verifiedAt` 说明信息是实时的，不是编的 |

**答辩时的一句话定位**：
> 市面上多数 AI 学习工具的输出是一段文本，用完就丢。我们把它做成了**有语义、有状态机、可被机器校验的格式**，于是计划才能被持续地执行、修订和协商。
