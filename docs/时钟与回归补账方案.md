# 第一部分 · B 的用户视角效果（不含实现）

这一部分只回答一个问题：**做完之后，学生看到的世界变成了什么样。**

## B-1 复盘从「一个常驻的页」变成「一件你决定什么时候做的事」

现在底部有四个 tab，复盘永远是第二个——不管这周有没有值得复盘的事，它都杵在那儿。

改完：

- 底部只剩三个：**今日 / 资源 / 文件**。
- 复盘入口出现在**今日页顶部**，而且**只在有理由的时候出现**：
  - 距上次复盘 ≥ 约定天数 → 一条不起眼的提示条：「上次复盘是 3 天前 · 现在聊聊？」
  - 刚复盘过 → 什么都不显示。
- 点进去之后，复盘是**一个有开始有结束的过程**（一问一答地把这周过一遍，最后给出调整建议并确认），不是一屏随时可以回来偷看的报表。走完回到今日页，提示条消失。

效果上：复盘从「一个功能」变成「一件仪式」。学生不会觉得有个东西一直在催他，也不会觉得有个页面他从来没打开过。

## B-2 可以直接跟自己的计划说话

这是变化最大的一块。现在学生**没有任何办法跟 AI 说话**——访谈是计划生成之前的一次性线性问答，复盘是只读的。计划生成完之后，学生和系统之间就只剩「打勾」和「改时长」两个动作。

改完，今日页右下角常驻一个入口（「跟 AI 说说」）。走一遍：

> **学生打字**：周三晚上有事，把周三那两项挪到周末。另外目标改成省二就行，别冲省一了。

> **界面回一张待确认卡**：
> 　我先说一遍我听懂了什么：周三的两项推到周末，目标从「冲省一」改成「保省二」。
> 　
> 　准备做的改动：
> 　　□ 复习：背包三变体回忆默写 　10/21 周三 → 10/24 周六
> 　　□ 01 背包手推 5 遍 + 做 3 道模板题 　10/21 周三 → 10/25 周日
> 　　□ 目标 　「明年四月做出省赛中等难度的题」→ 保持原话，只改优先级：冲省一 → 保省二
> 　
> 　〔全部应用〕〔取消〕

- 每一行都能单独划掉（这条我不想改）。
- 点「全部应用」→ 计划真的变了，提示「已修改 3 处」，而且**可以撤销**——它和其他任何改动一样进了版本历史。
- **听不懂就直说**：「后半句我没把握——你是想改目标本身，还是想改截止日期？」它不会猜着改。
- **它做不了的事会明说**：比如「删掉整份计划重做」不在它能碰的范围内。

**自己改和让 AI 改是同一批能力，不是两套。** 学生不必经过 AI：点卡片 → 编辑页 → 改标题、备注、预估、日期、删掉这一项。能改的字段和 AI 能改的完全一致——所以不会出现「AI 能改但我改不了」这种憋屈事。

## B-3 它记得你说过的话

现在学生档案只活在内存里，**重开 App 就没了**。表现是：重新打开之后跟它商量，它不知道你什么水平、哪儿弱、每周有多少时间；找资料也只能从计划内容反推。

改完：重新打开之后，它仍然知道你是谁。而且这份记忆跟着**计划文件**走——把文件发给同学，他打开看到的是同一份上下文，不是一份只有日期没有来由的任务表。

## B-4 降级不再像报错

现在流程中间会冒出一句「没连上服务端（请求超时（25 秒）），用本机题库继续」。它很诚实，但它出现在学生正在答题的时候，读起来像出错了。

改完：平时只显示一个不起眼的小标——「AI」或「本机」。想知道为什么，点一下才展开那句话。

**但「这个结果是 AI 给的还是本机算法给的」永远看得见**，这是我们的底线，不能藏起来。变的只是它不再打断人。

# 第二部分 · A：时钟

## 2.1 为什么必须两种模式

因为这两个需求是**互斥**的：

- 演示和调试需要「今天就是 2026-10-19」，需要能任意前进后退，需要可复现；
- 真实使用需要「今天就是今天」。

把它们做成同一个东西（现在就是这样：`DEMO_TODAY` 是个写死的常量），结果是两边都不满意——真实使用时日期是假的，调试时又只能靠改源码。

所以把它变成一个**显式的、二选一的设置**，而不是一个藏在代码里的常量。这也是「时间固定由设置提供」的准确含义。

## 2.2 模式定义

|         | 调试模式                       | 正常模式                 |
| ------- | -------------------------- | -------------------- |
| 「今天」从哪来 | 设置里手填的日期                   | 服务端 `GET /time`      |
| 会自己走吗   | **不会**。填了 10/19 就永远是 10/19 | 会。回到前台时重新对表          |
| 用途      | 开发、演示、复现 bug、模拟隔了几天        | 真实使用                 |
| 服务端连不上  | 不影响（本来就不问服务端）              | 退回设备时间，并在界面上标明「本机时间」 |

**关键取舍：调试模式下「今天」不随时间流逝。** 如果它也会自己走，那「模拟隔了 5 天」就变成一个会自己消失的状态，调试和演示都没法依赖它。想要时间前进，就手填一个新的日期——**前进和后退都是同一个操作**，这也让「回到演示开始那天重演一遍」成为可能。

## 2.3 服务端 `GET /time`

```json
{
  "ok": true,
  "nowUtc": "2026-10-19T13:46:00Z",
  "offsetMinutes": 480,
  "today": "2026-10-19",
  "zone": "Asia/Shanghai"
}
```

四个字段各有理由：

- `nowUtc` + `offsetMinutes` 分开给，而不是给一个 `+08:00` 字符串。客户端只需要拿 `offsetMinutes` 去**手工格式化**（`nowUtc + offset` 然后取各字段），**不需要任何时区库**。这一点很重要：Hermes 的 `Intl` 支持依赖构建配置，不能让"今天是哪天"这种东西悬在一个可能不存在的 API 上。
- `today` **由服务端算好**再给。客户端永远不做「把一个 UTC 时刻换算成本地日期」这件事——那正是 `toISOString().slice(0, 10)` 在东八区晚上 8 点之后会算成"明天"的原因。**这个错误在服务端只可能犯一次，在客户端会犯很多次。**
- `zone` 只用来显示，不参与计算。

服务端侧的配置：

- `SP_TZ`（默认 `Asia/Shanghai`）——算 `today` 用。
- `SP_TODAY=2026-10-19`——**整台服务端的时间冻结在这一天**。这是把现在客户端那个假时钟搬到服务端、并且变成一个有文档的启动参数。
- 两者都不设 = 真实时间。

为什么服务端也要能冻结：正常模式的演示同样需要日期和示例计划对得上。如果不给这个开关，演示时就得回头去改客户端代码——那正是我们要消灭的东西。

**服务端自己的 `nowStamp()` 也要走同一个时钟。** 现在 `apps/server/src/routes/plan.ts` 和 `routes/interview.ts` 各自抄了一份 `nowStamp()`，都是裸的 `new Date()`。同一个「现在」在项目里有三份实现（还有 `codeforces.ts` 里的 `Date.now()`），冻结时间时必须一起冻结，否则会出现「计划是 10/19 生成的，但赛程按真实时间过滤」这种自相矛盾——**这个矛盾现在就已经存在了**。

## 2.4 客户端时钟的形状

一个对象，两种模式共用同一套接口：

```ts
type ClockReading = {
  today: string;                            // YYYY-MM-DD
  now: string;                              // 给 cmd.at 用
  source: 'setting' | 'server' | 'device';  // 界面要如实显示
};
```

**`now` 在两种模式下都用同一个机制：基准 + 单调递增的分钟游标。**

- 基准从哪来：调试模式 = 手填日期的当天上午；正常模式 = 服务端返回的 `nowUtc` + `offsetMinutes`；降级 = 设备时间。
- 每次取 `now()` 游标 +1 分钟。

为什么不用真实流逝的时间：因为**同一批操作要可复现**。真实时钟在两次点击之间会走掉几百毫秒，命令历史里的时间戳就变得每次都不一样，测试没法断言，演示也没法重演。游标保证「同一串操作产生同一串时间戳」。

正常模式下回到前台时重新对表（重新取服务端基准），游标跳到「不早于服务端 now + 1 分钟」——**这正是现在 `syncClockTo` 在做的事，但基准从「计划文件里的 updated」换成了「服务端」**。从计划反推时钟是个绕法，第二阶段会连根拆掉。

## 2.5 设置存在哪

**`settings.json`，和计划文件放在同一个目录**（复用同一套存储后端，所以原生和 web 各只有一份实现，不用为设置再写一遍平台代码）。

```json
{
  "clock": { "mode": "debug", "date": "2026-10-19" },
  "lastSeen": "2026-10-19"
}
```

**为什么不放进计划文件**：这两个都是**这台设备的使用状态**，不是计划的属性。

- 调试开关如果写进计划文件，那这份文件被复制到别人机器上时会**带着调试模式一起过去**，对方打开看到的是一个冻结的日期。
- `lastSeen`（上次打开）如果写进计划，那么「我今天打开过一次」这件事会**让版本号 +1**。版本历史是给人看的，「我看了一眼提示」不该在里面占一行——和 `plan.attachResources` 当初被做成一条命令而不是十几条是同一个道理。

计划文件因此**一个字段都不用加，schema 不用动版本**。

## 2.6 界面放哪

文件页（`(tabs)/file.tsx`）已经有一个「演示用」区块，时钟设置并进那里，成为「时间」区块：

- 模式：`跟随服务器` / `固定日期`
- 固定日期时的日期选择（复用访谈页那个日期控件，不新写）
- 当前读数：`2026-10-19（来自设置）` / `2026-10-04（来自服务器）` / `本机时间（没连上服务器）`
- 〔模拟隔了 5 天回来〕——见 3.7

# 第三部分 · A：回归补账

## 3.1 触发条件

App 启动、计划读回来之后：

```
daysPassed = daysBetween(settings.lastSeen, today)
daysPassed >= 1  且  plan 里确实存在受影响的任务
  → 自动进入补账页
```

两个条件都要满足。只满足第一个（比如隔了 5 天但计划里全是已完成/已放弃的任务）就不该拿一个空页面拦人。

`lastSeen` 缺失（新设备、第一次跑）→ 不触发。理由是**没有"上次"就没有"这段时间"**，硬拿 `meta.created` 当基准会在第一次打开时弹出一个莫名其妙的页面。

`daysPassed <= 0`（调试模式把日期往回拨）→ **不触发**。往回拨是调试动作，不是一个需要结算的时间段。

## 3.2 引擎要算的事实，和模型要说的话

这一屏的内容分两层，边界必须清楚：

**引擎算（可单测、可复现、模型不许改）：**

- 过了几天
- 本该完成但没完成的清单：`scheduledFor ∈ [lastSeen+1, today]` 且 `status ∉ {done, skipped}`
- 其中每一项挡着几个后续任务（依赖链长度）
- 有没有项目已经超过 `goal.deadline`
- 有没有里程碑因此有风险
- 如果选择「压缩到接下来几天」，压完会不会超出 `constraints.weeklyMinutes`

**模型只做一件事**：把上面这堆数字写成一段人话。数字从引擎来，模型**只改措辞**。

这是项目里已经有的模式（`/plan/review` 就是引擎算 `engineView`、模型写 `narrative`），照抄即可。理由也一样：模型数数不可靠，而「到底有几项没做」是这一屏唯一不能错的东西。

## 3.3 一屏交互，以及默认值

顺序是：**先说发生了什么 → 再让学生纠正 → 最后问怎么办。**

```
┌──────────────────────────────────────────┐
│ 距上次打开过了 5 天                        │
│                                           │
│ 这 5 天里本该做完 9 项，现在都没打勾。      │
│ 其中 2 项挡着后面的任务。                  │
│                                           │
│ ── 这 9 项，实际情况是 ─────────────────   │
│   o 复习：背包三变体回忆默写      10/15    │
│   o 01 背包手推 5 遍             10/16    │
│   o 图论：最短路四算法            10/17    │
│   …                                       │
│   〔都没做〕〔全部标记为做完〕              │
│                                           │
│ ── 接下来怎么办 ───────────────────────    │
│   (•) 放回待排池，重新排    ← 默认         │
│   ( ) 压缩到接下来 3 天    会超载 1 天      │
│   ( ) 先不动，我自己安排                    │
│                                           │
│                    〔确认〕                │
└──────────────────────────────────────────┘
```

**默认值是「都没做」。** 这是这一屏最重要的一个决定：

- 它是**无损**的默认——任务不会丢，也不会被错误记账；
- 它让**最常见的情况是零次额外操作**：隔了几天回来，多数时候就是真的一项都没做，直接点确认；
- 反过来「逐项问做了没」在隔了 5 天、9 项的情况下会变成 9 次问答，和「简洁的交互」正面冲突。

需要纠正的学生只需要勾出「其实我做了的」那几项，点〔都没做〕也可以先把全部清空。

## 3.4 「放弃」不是删除

学生标记「放弃」的项目 → `status = 'skipped'`，**不物理删除**。

- 它从排期里消失（引擎不再安排 `skipped` 的任务）；
- 但它留在计划文件里，复盘页能说「你放弃了 3 项」；
- 它也不会污染完成率——`skipped` 和 `done` 是两个不同的状态，本来就分得开。

物理删除会把「学生主动放弃」和「这个任务从来没存在过」变成同一件事。这两件事在复盘时是完全不同的信息：前者是学生对自己节奏的判断，后者只是数据少了。

## 3.5 一条命令，不是十二条

新增一条命令：

```ts
| {
    type: 'plan.settle';
    at: string;
    /** 结算覆盖的日期区间 */
    from: string;
    to: string;
    /** 学生勾了「其实做完了」的 */
    done: string[];
    /** 学生勾了「放弃」的 */
    skipped: string[];
    /** 剩下的怎么办 */
    carry: 'backlog' | 'compress' | 'hold';
    /** 顺带留一条复盘记录 */
    review: PlanFile['reviews'][number];
  }
```

**必须是原子的一条。** 12 项各发一条命令会得到：

- 12 个版本号 —— 版本历史页变成 12 行，看不出这是一次结算；
- 12 个快照占用；
- **一次回滚回不到整批之前** —— 学生发现结算错了，得回滚 12 次，而中间任何一次失败都会停在半路。

这和 `plan.attachResources` 当初被做成一条命令而不是「`resource.add` + `task.edit` 循环」是同一个论证，这里只是规模更大。

结算完成后写 `settings.lastSeen = today`。写的是**设备设置**不是计划——理由见 2.5。

## 3.6 「先不动，我自己安排」也要写一条记录

`carry: 'hold'` 时任务留在原地不做任何重排。但它仍然走 `plan.settle`，因为**「我看到了，我决定不管」本身是一个决定**，需要留在历史里。否则过两周回头看，会以为那时候系统没提醒。

## 3.7 演示当天怎么办

演示没法真的等一天。文件页的「时间」区块里放一个：

> 〔模拟隔了 5 天回来〕

它做两件事：把调试日期设成 `今天 + 5`，把 `settings.lastSeen` 往回拨 5 天，然后触发结算。**这同时是演示这个功能的开关和这个功能的测试入口**——一个按钮同时服务演示和验证，比造两个入口好。

## 3.8 不做什么

- **不做后台定时任务、不做本地通知。** 「主动」是通过「打开时结算」实现的，不是通过闹钟。理由：通知需要权限申请、平台配置、真机验证，而这三样在参赛现场一样都不能出错，收益却只是把「打开时提醒」提前了几小时。
- **不做「每 N 天自动复盘」。** 复盘的节奏应该是学生自己的事（B-1 已经把发起权交还给人），补账是**系统的**职责——它是把被时间冲掉的事实对齐，不是替学生安排。
- **不把结算历史单独存一份。** 一条 `Review` 记录够了，多一份就是多一个会不一致的地方。

# 第四部分 · 拆掉时间守卫（这是整个方案的地基）

## 4.1 那条规则在做什么，为什么现在成了障碍

```ts
if (cmd.at < plan.meta.updated) {
  return { ok: false, error: `命令时间 ${cmd.at} 早于计划更新时间 ${plan.meta.updated}` };
}
```

它的目的是防止乱序写入把版本号推回去。代价是**它逼着「命令时间」必须是真实递增的**，于是必须养一个假时钟——`clock.ts` 那个单调游标、`DEMO_TODAY` 常量、`syncClockTo`、以及示例计划里写死的 2026-10 时间戳。

而调试模式要求**时间可以被任意回拨**。这条守卫和调试模式是**直接冲突**的：把日期拨回 10/19 之后，每一条命令都会被拒掉，界面表现就是「点了没反应」——和当初那个假时钟要解决的问题一模一样。

还有一个已经存在的事实错误：`Meta.updated` 的注释写着「本地时区的展示用时间戳，**仅用于 UI，不参与排序逻辑**」。它其实参与了，而且是硬拒绝。

## 4.2 拆掉之后谁保证不乱序写

**先说结论：现在没有任何地方真的需要这条守卫。**

- 客户端：`apply` 是同步 reducer，`state.plan` 顺序传递，两条命令不可能并发。**没有风险。**
- 服务端生成的计划：`installPlan` 直接替换整份计划——它**根本不走 `applyCommand`**，所以这条守卫**从来就没保护过它**。

所以正确的做法是：**删掉这条守卫，并且不发明一个替代品。**

不加「命令带 `expectVersion`」这类东西，因为当前架构里没有第二个写者，加了就是一个永远不会被触发的字段——而永远不会被触发的代码是最容易腐烂的。

## 4.3 但顺着这条线，发现了一个真的乱序写 bug

服务端生成计划要 20–40 秒。如果学生在这 40 秒里打了勾、改了时长，`installPlan` 回来时会**直接把这 40 秒里的所有修改覆盖掉**，而且不提示。

这才是真正需要防的乱序写，而且它现在就在。

修法：`installPlan` 前比对「请求发出时的修订号」和「现在的修订号」。不一致就不静默装进去，而是问学生：

> 生成计划期间你改了 2 处。新计划会覆盖它们。〔用新计划覆盖〕〔保留我的修改，放弃这次生成〕

## 4.4 连带必须改的地方

删掉守卫不是删一行就完事，以下每一处都是因为「时钟不再必然递增」而必须处理的：

1. **`meta.updated` 可能倒退。** 它现在的定义就是「最后一次写入的时间」，调试模式下回拨日期之后它会往回走。这是**正确的**——它是一个逻辑时钟，不是墙上时钟。要做的只是把注释改对，并且确认**没有任何地方拿它做比较**（现在唯一的比较就是被删掉的那条守卫）。
2. **`history[].at` 可能非单调。** 同上，只影响人读历史，不影响任何逻辑。
3. **所有日期差的计算都要允许负数。** `daysBetween` 统一实现，返回可正可负，由调用方决定怎么处理（补账那条路上是「≤0 就不触发」）。
4. **`codeforces.ts` 里的 `Date.now()` 必须换成传入的 `today`。** 这是一个现存的内部矛盾：同一个「今天」在同一个请求里有三个来源（客户端传的 `today`、服务端自己的 `nowStamp()`、这里的 `Date.now()`）。不统一的话，调试模式下实时赛程会全部显示「已截止」——**这个 bug 上个月已经真实发生过一次**，当时的处理是在标题里保留日期 + 抑制倒计时，那是个绕过，不是修复。
5. **服务端两处重复的 `nowStamp()` 合并成一处**，并且接上 `SP_TODAY`。
6. **`onboarding.tsx` 里的 `nowStamp()`** 换成时钟读数。
7. **`syncClockTo(plan.meta.updated)` 删掉。** 它的存在只是为了绕过那条守卫；守卫没了，从计划反推时钟这个绕法就没有理由了。

# 第七部分 · 验证

**单元测试（shared）**

- `daysBetween`：跨月、跨年、同一天、负数
- `formatStamp`：东八区、西五区、`offsetMinutes = 0`

- 时钟游标：同一串操作产生同一串时间戳（可复现性）

**单元测试（server）**

- `/time` 在 `SP_TODAY` 下的返回；`SP_TZ` 影响 `today` 但不影响 `nowUtc`
- UTC 23:00 时 `today` 应该是东八区的次日（**这条测试就是用来钉死 `toISOString().slice(0,10)` 那个错误的**）
- `codeforces` 在传入的 `today` 下过滤，且不再读 `Date.now()`

**端到端**

- 把调试日期设成 D，走一轮正常操作
- 把日期改成 D+5，重载 → 断言补账页出现、清单项数与引擎算的一致
- 确认 → 断言版本 +1（**只 +1**）、任务回到待排池、`lastSeen` 已更新
- **把日期往回拨到 D** → 断言不再触发补账、且后续操作仍然正常（**这一条直接验证 4.1 那个冲突已经消失**）

# 第八部分 · 这一轮明确不做的事

| 不做                      | 理由                                         |
| ----------------------- | ------------------------------------------ |
| 后台定时任务 / 本地通知           | 需要权限、平台配置、真机验证，三样在现场都不能出错；收益只是把提醒提前几小时     |
| 计划文件加时间相关字段             | 调试开关和 `lastSeen` 是设备状态，进计划会污染版本历史、还会跟着文件传播 |
| `Command.expectVersion` | 当前架构里没有第二个写者，加了就是永不触发的代码                   |
| 跨时区自动换算                 | `today` 由服务端算好；客户端只做算术，不碰 `Intl`           |
| 用真实流逝时间做 `cmd.at`       | 会让命令历史不可复现，测试没法断言、演示没法重演                   |
